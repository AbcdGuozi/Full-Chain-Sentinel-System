# 安全测试报告格式合并规则（通用厂商报告章节 + clown 8 块）

> 本文件是 Full-Chain 的报告写作规范。漏洞通过 `vuln_submit` 入库，导出由 `packages/web/src/vulnerability-markdown.ts` 生成。外层采用通用厂商报告章节结构，内层每个漏洞采用 clown 的 8 块结构。所有未提供的事实一律写 `待补充`，不得根据经验补全。

## 1. 总原则

- **只写已提供的事实**：标题、URL、等级、描述、危害、接口、步骤、整包、修复建议均来自当前运行数据或人工输入。
- **缺字段写 `待补充`**：缺少任何必填内容时输出 `待补充`，并说明需要补充什么；不得用"常见情况""通常""推测"替代。
- **空数据不等于安全**：`findings` 为空时只能写"本次未记录安全问题"，不能写"系统不存在漏洞""系统安全"。
- **等级只有四级**：漏洞正文的等级只允许 `严重`、`高危`、`中危`、`低危`。`无威胁` 只用于摘要统计，不作为单个漏洞的正文等级。
- **输出编码**：使用 UTF-8 + LF；需要交给只接受 CRLF 的工具时再转换。
- **标题层级只用 `#`、`##`、`###`**：封面用 `#`，章用 `##`，小节和漏洞用 `###`。
- **整包用 ` ```http ` 代码块**：每个复现步骤最多一个整包，不使用其它语言标记。

## 2. 合并后的章节骨架

```text
# <文档名称>                        封面标题
| 测试时间 | 测试范围 | 文档编号 | 版本 | 日期 |
## 一、摘要
## 二、安全问题
### 2.1 <漏洞标题>
### 2.2 <漏洞标题>
## 三、总结
### 3.1 问题分布
### 3.2 修复优先级
## 附录A 风险等级说明
## 附录B 问题等级说明
```

- 漏洞章节编号连续：`2.1`、`2.2`、`2.3`，不跳号。
- 通用厂商报告章节负责“报告整体长什么样”；clown 8 块负责“单个漏洞怎么写”。
- 不额外增加通用厂商报告模板之外的章节；需要说明的内容放进对应小节。
- 已移除“项目信息”和“项目概述”章节，不再渲染委托方、测评方字段。

## 3. 封面与文档信息（必填）

| 字段 | 来源示例 | 缺失处理 | 禁止 |
|---|---|---|---|
| 项目名称 | `meta.projectName`、`meta.project` | `待补充` | 用目标域名代替项目名 |
| 文档名称 | `meta.documentName`、`meta.docName`；否则由 `reportTitle(run)` 生成 | `待补充`（run 为空时） | 编造客户名、系统名 |
| 文档编号 | `meta.documentNumber`、`meta.docNumber` | `待补充` | 自动生成看似正式的编号 |
| 版本 | `meta.version`、`meta.docVersion` | `待补充` | 默认写 `1.0` 冒充已定稿 |
| 日期 | `meta.date`、`run.updatedAt`、`run.createdAt` | `待补充` | 填当前日期冒充测试日期 |

- 封面表格中每个单元格都不能为空；空值统一 `待补充`。
- 文档编号、版本、日期属于审计信息，**不得编造**。
- `meta.client`、`meta.assessor` 仍可传入以保持兼容，但**不渲染**。

## 4. 摘要

必填内容：

1. 测试对象、测试日期。
2. 五类数量：`严重漏洞`、`高危漏洞`、`中危漏洞`、`低危漏洞`、`无威胁`。
3. 汇总表：`威胁级别 | 数量 | 安全问题名称`。
4. 总体状态：`紧急`、`高`、`中`、`低`。

计数规则：

| 输入等级 | 计数键 |
|---|---|
| `critical` / `严重` | `critical` |
| `high` / `高危` | `high` |
| `medium` / `中危` | `medium` |
| `low` / `低危` | `low` |
| `info` / `无威胁` / `none` | `info` |
| 未知、空值 | `medium`（按中危） |

- `severityCounts(findings)` 只返回 `{critical, high, medium, low, info}` 五个数字，合计由调用方自行求和。
- 总体状态映射：存在严重 → `紧急`；否则存在高危 → `高`；否则存在中危 → `中`；其余（含仅低危、无问题）→ `低`。
- 汇总表中的问题名称按等级分组；没有该等级时写 `—`，不虚构问题。
- 摘要中的数量必须来自实际 `findings`，不得手填。

## 5. 单个漏洞的 8 块（clown）

每个漏洞按以下顺序输出，顺序不可调换：

| 块 | 必填 | 写法 | 缺失处理 | 禁止 |
|---|---|---|---|---|
| 漏洞标题 | 是 | 一行，写"谁的站、做成了什么"；有会话写"越权"，无会话才可写"匿名未授权" | `待补充` | 用"未登录"冒充"未授权"；有会话仍写匿名 |
| 目标网站URL | 是 | `目标网站URL：https://...`，写人可直接打开的完整地址 | `待补充` | 拼接、猜测、用历史 URL |
| 漏洞等级 | 是 | 只写 `严重/高危/中危/低危` | 未知按 `中危` | 写"信息级""无威胁"作为漏洞等级 |
| 漏洞描述 | 是 | `漏洞描述：` 单独一行，冒号后换行；第一人称"我"写做成了什么；有会话写"我拿自己的会话"，无会话写"我没登录" | `待补充：本报告未记录该漏洞的漏洞描述...` | 说明书腔；写"攻击者"；把接口表、复现步骤、危害清单抄进描述；编造请求/响应 |
| 漏洞危害 | 是 | `漏洞危害：` 单独一行，冒号后换行；**每种伤害单独一行**；写最终能造成的伤害，不写步骤 | `待补充：本报告未记录该漏洞的具体危害...` | 写"第一层/第二层"；写"不限于""等敏感信息"；编造未验证的姓名、手机号、金额、删除动作 |
| 涉及接口清单 | 是 | 按 `1. 2. 3.` 编号；每条写完整地址和出处（JS 链接或页面 URL） | `1. 待补充` | 列出没真正打过的接口；只写文件名；编造路径或参数 |
| 复现步骤 | 是 | 每条步骤一两句，说明"打了什么、等于证明了什么"；**每步一个 ` ```http ` 整包** | `待补充：本报告未记录该漏洞的复现步骤。` | 贴响应包；写"预期"；一步贴多个包；编造请求头、Cookie、命令输出 |
| 修复建议 | 是 | 针对当前漏洞，简短、可落地 | `待补充：本报告未记录修复建议...` | 套话；建议与漏洞成因无关；建议真实攻击操作 |

### 6.1 描述的硬规则

- 有登录态：用"我拿自己的会话换成别人的对象做成了什么"，不得写"我没登录"。
- 无登录态：用"我没登录做成了什么"；标题才写"匿名未授权"，描述里不重复贴类型。
- 描述只讲事实和结果，不抄接口清单，不贴整包，不列危害清单。
- 凭据、密钥、硬编码口令若来自前端 JS：描述里必须给出完整实值和完整 JS 地址；**但报告返回值中的敏感请求头必须脱敏**（见第 8 节）。实值是否进入最终交付件由人工在受控环境决定，不写入知识库。
- 描述为空时只能输出占位说明，不能根据标题自动扩写。

### 6.2 危害的硬规则

- 只写"这扇门打开后能造成的最终伤害"：能读什么、能改什么、能删什么、能拿到什么身份。
- 每种伤害单独一行，使用 `-` 列表。
- 没有实际验证的权限面可以按真实权限描述，但不得编造具体受害者、数据条数、金额或操作结果。
- 没有证据时不要写"可批量""可删除"等超出验证范围的结论；拿不准就不写。
- 危害为空时输出占位说明，不复制描述充当危害。

### 6.3 接口清单与复现步骤

- 接口清单只列复现步骤中真正使用过的接口，按使用顺序编号。
- 每条接口写完整 URL；取自 JS 的附完整 JS 链接，取自页面的附页面 URL。
- 复现步骤每步只做一件事，描述里写清参数来源；不要反复写"不登录/不带 Cookie"。
- 每步只贴一个可复制整包，代码块语言固定为 `http`。
- 整包只包含实际提供的请求行、请求头和请求体；**不自动补 User-Agent、Accept、Content-Length 等未提供的头**。
- 不贴响应包、不写"预期返回"、不写命令输出；证据不足就写 `待补充`。
- 缺少整包时仍保留一个 `http` 代码块，内容写 `待补充`，不得生成示例包。

### 6.4 修复建议

- 必须针对当前漏洞的根因，例如：服务端对象归属校验、参数化查询、输出编码、最小权限、传输加密。
- 不写"加强安全意识""定期扫描"这类无法验收的套话。
- 不写利用代码、绕过步骤或攻击命令。

## 6. 等级归一化

`normalizeFinding(finding)` 的映射：

| 输入 | 输出 |
|---|---|
| `critical`、`Critical`、`严重` | `严重` |
| `high`、`High`、`高危` | `高危` |
| `medium`、`Medium`、`中危` | `中危` |
| `low`、`Low`、`低危` | `低危` |
| 未知、空值 | `中危` |

- 输出等级不得出现第五种值。
- `info`/`无威胁` 只在 `severityCounts` 中计入 `info`；若作为单个 finding 渲染，按未知等级回退为 `中危`，避免正文出现第五级。
- 等级不能因为"多了一个字段"而跳档；定级依据必须是已验证的影响。

## 7. 脱敏与证据边界

- 请求头 `authorization`、`cookie`、`set-cookie`、`x-api-key` 只保留**前 6 个字符 + 长度**，例如 `Cookie: sessio…（已脱敏，长度 20）`。
- 请求体最多保留前 4096 字节；超长时追加截断说明。
- JSON 或表单字段名为 `password`、`passwd`、`pwd`、`token`、`secret`、`api_key`、`cookie`、`session` 等时，值同样脱敏。
- 证据中禁止出现账号密码原文、完整 Cookie、完整 Token、私钥、数据库连接串。
- 截图、命令输出、响应包只能引用真实存在的证据；没有就写 `待补充`，不得描述"类似截图"。

## 8. 禁止编造清单（必须逐项检查）

以下内容没有输入证据时**一律禁止生成**：

1. 目标 URL、接口路径、参数名、参数值、Host、端口。
2. 请求方法、请求头、Cookie、Token、会话、账号、密码。
3. HTTP 状态码、响应体、响应长度、命令输出、数据库内容。
4. 截图、日志、抓包结果、时间戳、测试人员。
5. 受影响人数、数据条数、金额、业务名称、内部系统名。
6. 测试依据、测试工具、测试日期、文档编号、版本号。
7. 未实际验证的利用链、权限提升、批量能力、删除/修改结果。
8. 从历史报告、其它项目、模型记忆推断出的"常见漏洞"。

允许的替代写法：

- 缺内容：`待补充`
- 缺描述：`待补充：本报告未记录该漏洞的漏洞描述，需由测试人员根据实际验证结果补充。`
- 缺危害：`- 待补充：本报告未记录该漏洞的具体危害，需由测试人员补充。`
- 缺步骤：`待补充：本报告未记录该漏洞的复现步骤。`
- 无 findings：`本次未记录安全问题。`
- 无汇总项：`—`

## 9. 字段兼容别名

`normalizeFinding` 可识别以下常见别名，便于上游 agent 输出：

| 规范字段 | 兼容输入 |
|---|---|
| `title` | `name`、`vulnTitle`、`vulnerability`、`summary` |
| `targetUrl` | `targetURL`、`url`、`target`、`address` |
| `severity` | `level`、`risk`、`riskLevel` |
| `description` | `desc`、`detail`、`abstract` |
| `impacts` | `impact`、`harm`、`harms`、`damage`、`hazards` |
| `endpoints` | `interfaces`、`apiList`、`apis`、`endpointList` |
| `steps` | `reproduce`、`reproduction`、`repro`、`reproSteps`、`poc` |
| `remediation` | `fix`、`fixSuggestion`、`suggestion`、`recommendation`、`solution` |

- 别名只是兼容入口，不改变"缺字段写 `待补充`"的规则。
- 步骤对象可用 `description`/`desc`/`title`/`text`/`summary` 作为步骤说明，用 `request`/`raw`/`package`/`http`/`requestRaw`/`rawRequest` 作为整包。
- 接口对象可用 `method`、`url`、`source`、`note`。

## 10. 交付前检查表

- [ ] 封面七项齐全，缺失项为 `待补充`。
- [ ] 摘要五类数量与 `severityCounts` 一致，合计等于 findings 数量。
- [ ] 汇总表按严重/高危/中危/低危/无威胁分组，无虚构名称。
- [ ] 总体状态只取 `紧急/高/中/低`。
- [ ] 每个漏洞有 8 块，顺序正确。
- [ ] 描述为第一人称，`漏洞描述：` 冒号后换行。
- [ ] 危害每种伤害单独一行。
- [ ] 接口清单按 1、2、3 编号且写完整 URL。
- [ ] 每个复现步骤恰好一个 ` ```http ` 代码块。
- [ ] 全文无 `undefined`、`[object Object]`。
- [ ] 换行符与导出工具一致。
- [ ] 敏感请求头与请求体已脱敏。
- [ ] 没有任何未提供却出现的 URL、数据、命令输出、人员、日期。

## 11. 验证

用 `vuln_submit` 提交一条测试记录后导出报告，检查：等级、CVSS、目标、原始数据包、复现步骤、证据、修复建议齐全；空记录只写“本次未记录安全问题”；渲染结果不含 `undefined` 或 `[object Object]`。
